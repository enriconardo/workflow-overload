# Backlog

- **`junit.py`: read the failure type of pytest's JUnit XML.** pytest writes no `type` on a `<failure>` (checked with pytest 9.2): `<failure message="assert 1 == 2">`, `<failure message="NotImplementedError">`. The type is only in the failure's text, whose last line, with the default traceback, is `<path>:<line>: <Type>` (`test_x.py:5: AssertionError`). `junit.py` reads only the attribute, so every pytest failure comes out "red for the wrong reason, no type" and no red check on pytest is ever valid, though `phases/init.md` names pytest's `--junitxml`. With no `type`, the type comes from that last line. And pytest stops the whole run at a collection error: one file that does not load hides the results of the others, so the pytest example of `phases/init.md` gains `--continue-on-collection-errors`. Before the config v2 and setup items, whose measure of `red_types` reads these types. Source: probe of pytest during the review of the config v2 item.
- **Config version 2: the plugin calls the project's mechanisms, it does not reimplement them.** Every key discussed; the v2 config: `version`, `check`, `run_tests`, `main`, `integrate`, `rules`, `backlog`, `tests_glob`, `red_types`. The plugin owns *when* a check runs and the process invariants (commit only the verified tree, the suite untouched, a clean main, `--no-ff`); the project owns naming, message formats and what its checks do. This item changes the keys, the scripts, the phases and the agents; how a project finds its values (looking for `check`, measuring `red_types`, the gaps of its rule files) is the setup item's, which rewrites `phases/init.md`. Decided so far:
  - Drop `commit`, `commit_types`, `subject_max`: the model writes the message following the project's `rules`, and the project's `commit-msg` hook, if any, enforces it. `commit.sh` keeps the process checks only (verified tree, suite intact, non-empty message), and checks the tree once more after the commit: a `pre-commit` hook that rewrites staged files (lint-staged, a formatter) changes it after the check, so a commit whose tree is not the verified one is undone (`git reset --soft HEAD^`) and refused, with the files the hook changed.
  - Drop `types` and `branch`: the model composes the branch's name following the project's `rules`, as it does a commit message, and `branch.sh <S|L> <name> <intent-file>` takes it whole. No script reads a part of a name; it is only used whole (journal, merge subject, metrics, `refs/overload/suite/<branch>`): `metrics.py git` drops its `type` field, today `branch.split("/")[0]`, which a name without a type turns into noise. `branch.sh` keeps the process checks only: `git check-ref-format`, not existing yet, not `main`, started from a clean, up-to-date main. Gone: the template, the fixed kebab-case of scope and description, the ticket pattern. The merge subject's length becomes the project's hook's: `branch.sh` runs the project's `commit-msg` hook on `Merge branch '<name>'` (`git hook run --ignore-missing commit-msg -- <file>`, which follows `core.hooksPath`), so that a name the hook would refuse at the merge is refused before the task, not after it. `git hook run` needs git 2.36; with an older git the check is skipped, and `branch.sh` says so.
  - Rules that state no convention: a branch `<type>/<description>`, kebab-case; a subject in the imperative, at most 72 characters. The fallback is written once, in `SKILL.md`, which every phase reads; the setup proposes the conventions for the rule files, so that it is rarely needed.
  - Drop `exec`: a container prefix goes inside the commands (`check = docker compose exec app make check`); that commands run in a container is the project's knowledge, in its CLAUDE.md, which the setup proposes to add when missing; a session without Docker is the project's wrapper's job, or `OVERLOAD_CHECK` and `OVERLOAD_RUN_TESTS`. Custom subagents load the CLAUDE.md files by default (Claude Code docs, *Subagents*: only the built-in Explore and Plan skip them), so the plugin's agents know it too: the step-implementer installs a dependency as the rules say, not through a prefix it is given.
  - Rename `verify` to `check`: the key is the project's command, `verify` stays the plugin's step that runs it and records the tree.
  - `check` always checks everything: a scoped command has no base to compare with, and on main (the setup, the merge in `integrate.sh`) it would check nothing. If it proves too slow, a `{base}` placeholder, as `{files}` in `run_tests`.
  - `check` is the commit gate, a local subset of what the CI runs: exit 0 green, else red; ends on its own (no watch mode, no prompt); changes no file (`--check`, not `--fix`); local, no secrets or services; fast enough for every commit; deterministic; the cause of a red in its last lines. `verify.sh` enforces the one it can: it hashes the tree again after the run, and a run that changed a file git does not ignore is red, with the files it changed (a snapshot written without `--ci`, a `--fix`, a report not ignored). The README gets a *check* section for a first install: the contract, examples, and how to try it on a clean main.
  - `integrate` stays as it is: `merge` only, and any other value refused with "not supported yet". Not to be ready for the integrations to come, since a key added later with a default breaks no config, but because it names the one mode the process is built on.
  - `main` stays a key, default `main`, set by the human: the setup asks for it, never derives it unasked.
  - Drop `reference` and `specs`: the test-author's throwaway model is the plugin's own, fixed at `.workflow/reference`; the L specs are in the plugin's format, fixed at `.workflow/specs`. `backlog` stays, default `.workflow/backlog.md`: like `rules`, it points to a thing of the project, which may keep a backlog of its own.
  - Rename `test_files` to `run_tests`: it is a command, as `check`, not a list of files, and it stood next to `tests_glob`, which is one.
  - Drop `stub`: stubs never reach main (stub mode does not commit, the implementer replaces them before the chunk's commit), so they are the plugin's own, like `reference`. The convention is fixed: a stub's body only throws an error whose type the runner reports as `NotImplemented` (Python's `NotImplementedError`, read from pytest's report as the `junit.py` item says; in TypeScript `Object.assign(new Error('not implemented'), { name: 'NotImplemented' })`), each agent writing it in the project's language.
  - `red_types` stays, default `AssertionError, NotImplemented`: the names the project's runner gives an assertion and a stub, written by the setup, which measures them.
  - `tests_glob` stays: it tells which files are tests, for `suite.sh` to record the suite and `commit.sh` to protect it; the test-author gets it as a bound on where tests go.
  - Drop `probe_env`: no script read it, and the prober got it as a command with no contract on how to use it. The prober always works in a new temporary folder outside the repository, deleted at the end, and always inside an isolated environment of the language (a `venv`, a folder with its own `node_modules`), never a global install. Such a folder isolates the dependencies, not the code they run: a package goes in without its install scripts (`npm install --ignore-scripts`, `pip install --only-binary :all:` when a wheel exists). The runtime is the version the project declares (`.nvmrc`, `engines`, `requires-python`, its Dockerfile's image) when the host has it; the output names the environment and the runtime's version, and says when it differs from the project's, since an answer holds for the version it ran on.
  - `rules` stays: it points to the project's conventions, and with `commit` and `exec` gone it is the one channel for them. One fix here: a decision record goes in a folder of `rules` that already holds decision records, and with none it is not written and the human hears it at the spec's checkpoint (`l-plan.md` today reads a folder out of the list). What the setup looks for in it is that item's.
  - `version = 2`, one migration: `require_config` refuses version 1 and says what to change: `verify` becomes `check`, `test_files` becomes `run_tests`, an `exec` prefix goes into both, the other dropped keys go. It refuses as well a key it does not know, naming it, and for a v1 key its v2 name: a v2 config that kept `verify = make check` would run with an empty `check`, and every commit would pass unchecked; a typo does the same. A `check` left out is refused too: a project with no checks writes `check =`, empty, on purpose. The refusal says where to migrate: on main, or, for a task already open, on its branch in a commit of its own, since the hook refuses `git merge` while a journal exists and the branch cannot take main's.
  - Every key change goes in `lib.sh`, `status.sh` (its list of keys, and of those an environment variable overrides), the README, the key list of `phases/init.md` (the rest of it is the setup item's), the phases and agents that name a key (`SKILL.md`, `brainstorm.md`, `s-path.md`, `l-plan.md`, `l-chunk.md`, `step-implementer.md`, `step-test-author.md`, `prober.md`), and the tests. A test fails when a phase or an agent names a config key that `lib.sh` does not know.

- **`/overload setup` in place of `init`: an agent proposes the config, the human settles it.** After the `junit.py` and config v2 items, in the same release as config v2, which changes only the key list of `phases/init.md`: setup replaces the rest, and is how a project gets a v2 config. `init` is confused with Claude Code's own `/init`, which writes a CLAUDE.md. The flow:
  1. `/overload setup [guidance]` runs a new read-only agent, `setup-explorer`, with the human's guidance. It reads the project (manifests, CI workflows, scripts, `git log`, rule files) and returns the proposal whole, not pointers: a table of key, proposed value, source (`file:line`, or the command it came from) and certainty; questions only for what it could not settle, a key with no source being a question by construction; the gaps in the rule files (branch and commit conventions, how commands run: a container, a wrapper) with the text to add. Not an explorer returning `file:line` for the main agent to read: the same files would be read twice. The rules on what makes a good value live in this agent, as listed below.
  2. The main agent shows it; the human answers, counter-proposes, accepts or refuses. A subagent cannot talk to the human: the dialogue stays in the main agent, which applies the answers itself, reading a file at most, without running the agent again.
  3. On acceptance, the main agent writes the config and runs `verify.sh` on main, which must be green; no agent for one command, and a red needs the human.
  4. A new agent, `setup-red-probe` (Sonnet, low effort: a runner that does not collect a file needs a good retry, Haiku only after real runs), measures `red_types`: a test failing on an assertion, one calling a stub, one importing a missing module, in the project's language inside `tests_glob`, run twice through `run_tests`, then deleted. Not the prober, which may not work inside the repository. The types are read by a script, a new `junit.py --types-found` printing each test's failure type, not by the agent. The detection counts as reliable only when both types are present, the stub's is the one the convention says, neither shows up for the load error, and the two runs give the same types; then they go in `red_types`. Otherwise `run_tests` stays empty and the red check is skipped, as today, and the agent returns a diagnosis (a file not collected, the same type for an assertion and a load error) that the human hears; it changes no config.
  5. The results, the human's go, the commit, as today: the config and the backlog file; the text added to the rule files goes in a commit of its own.

  What the setup-explorer proposes, beyond what the table needs:
  - `check`: a command that meets the contract of the config v2 item, as the README's *check* section states it, with the parts it could not confirm (whether it ends on its own, whether it changes a file).
  - `main`: a question, proposing `main`, or the branch of `origin/HEAD` when it exists, with that source: `origin/HEAD` is missing or stale too often to be written unasked.
  - `rules`: what Claude Code does not load by itself: decision records, `CONTRIBUTING.md`, convention docs, and `AGENTS.md` only when a CLAUDE.md applies and does not import it, since with no CLAUDE.md Claude Code reads `AGENTS.md` itself (Claude Code docs, *Memory*). Open: whether `CLAUDE.md` stays in the default, since every agent loads the root one already, but not always the nested one a lesson would join.
  - `tests_glob`: the default shown is the one in `lib.sh`, never a copy of it in a phase.

  Source: review of the config's responsibilities, and its review.
- **`integrate`: pull or merge requests on GitHub, GitLab and Bitbucket.** Today `integrate.sh` merges locally with `--no-ff` and refuses any other value. A project that integrates by PR/MR cannot use the plugin. The value is not a switch: the process is built on the local merge, and each forge needs its own tool (`gh`, `glab`, Bitbucket's API). To design first: where the metrics line goes, since it rides on the merge commit and a protected `main` takes no commit from the plugin; who checks the merge's result, today `check` on it, then the CI; where the last checkpoint is, the conversation or the PR's review; what happens to the journal, today dropped by the merge; whether squash and rebase merges are allowed, since squash erases the one-logical-change commits. Source: review of the config's responsibilities.
