# Backlog

- **`integrate`: pull or merge requests on GitHub, GitLab and Bitbucket.** Today `integrate.sh` merges locally with `--no-ff` and refuses any other value. A project that integrates by PR/MR cannot use the plugin. The value is not a switch: the process is built on the local merge, and each forge needs its own tool (`gh`, `glab`, Bitbucket's API). To design first: where the metrics line goes, since it rides on the merge commit and a protected `main` takes no commit from the plugin; who checks the merge's result, today `check` on it, then the CI; where the last checkpoint is, the conversation or the PR's review; what happens to the journal, today dropped by the merge; whether squash and rebase merges are allowed, since squash erases the one-logical-change commits. Source: review of the config's responsibilities.
- **integrate: drop the stash of a task that turned L.** `phases/s-path.md`, *Turning L*, puts the S work in a stash named `S work`, and `phases/resume.md` does the same with `chunk <n>`. `integrate.sh` merges and deletes the branch but leaves the stash, so it stays in `git stash list` after the task. To design first: whether `integrate.sh` drops the stashes named after the task, or the phases drop them when their work is back in the tree. Source: the task that described the S to L switch.
- **`/overload bootstrap`: start a project that has no code yet.** `phases/setup.md` reads an existing project and needs `verify.sh` green on main, and `setup-red-probe` needs a test runner: on an empty repository there is no `check`, no `run_tests`, no `red_types`, and the red check, the core of the method, is skipped. A command of its own, separate from tasks: no branch, no journal. To design first: what it produces (a skeleton with build, test runner and one green test, or only the decisions and the config), who chooses the stack and how much it asks; whether it writes the first ADRs and the architecture document that `rules` then points to; whether it ends by running setup, or leaves it to `/overload setup`; how it stays within *The workflow starts only with `/overload`* (an argument of the one skill, like `setup`). Source: discussion on building whole applications with the workflow.
- **A level above the task: roadmap or epic.** Each task holds one spec; nothing carries architecture and order across tasks except the ADRs and the files of `rules`, and the code-explorer rebuilds the context from the code each time. On a whole application, cross-cutting decisions (data model, module boundaries, error conventions) can drift from task to task, and a single L task for the whole app overloads the spec review and the final review on `<base>..HEAD`. To design first: what the artifact is (a document under `.workflow/`, a set of ADRs, a list of future specs) and who writes and approves it; how a task links to its item, and what the brainstorm, the spec reviewer and the close read of it; whether the close updates it, and how it differs from the backlog; how it fits the single entry point without making `/overload` heavier for one-off tasks. Source: discussion on building whole applications with the workflow.
