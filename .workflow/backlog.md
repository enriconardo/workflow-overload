# Backlog

- **metrics.py: drop the project-specific default of `--verify`.** The default regex (`scripts/metrics.py`, the `--verify` argument) matches `./dev.sh exec` and `pnpm verify`, one project's commands, in a public plugin. It should match only the plugin's own steps, `verify.sh` and `integrate.sh`. Source: review of the config's responsibilities.
- **Config version 2: the plugin calls the project's mechanisms, it does not reimplement them.** Every key discussed; the v2 config: `version`, `check`, `run_tests`, `main`, `integrate`, `rules`, `backlog`, `tests_glob`, and `red_types` written by `init`. The plugin owns *when* a check runs and the process invariants (commit only the verified tree, the suite untouched, a clean main, `--no-ff`); the project owns naming, message formats and what its checks do. Decided so far:
  - Drop `commit`, `commit_types`, `subject_max`: the model writes the message following the project's `rules`, and the project's `commit-msg` hook, if any, enforces it. `commit.sh` keeps the process checks only (verified tree, suite intact, non-empty message).
  - Drop `types` and `branch`: the model composes the branch's name following the project's `rules`, as it does a commit message, and `branch.sh <S|L> <name> <intent-file>` takes it whole. No script reads a type or a scope out of a name; it is only used whole (journal, merge subject, metrics, `refs/overload/suite/<branch>`). `branch.sh` keeps the process checks only: `git check-ref-format`, not existing yet, not `main`, started from a clean, up-to-date main. Gone: the template, the fixed kebab-case of scope and description, the ticket pattern, the merge-subject length.
  - Drop `exec`: a container prefix goes inside the commands (`check = docker compose exec app make check`); that commands run in a container is the project's knowledge, in its CLAUDE.md, which `init` proposes to add when missing; a session without Docker is the project's wrapper's job, or `OVERLOAD_CHECK` and `OVERLOAD_RUN_TESTS`.
  - Rename `verify` to `check`: the key is the project's command, `verify` stays the plugin's step that runs it and records the tree.
  - `check` always checks everything: a scoped command has no base to compare with, and on main (`init`, the merge in `integrate.sh`) it would check nothing. If it proves too slow, a `{base}` placeholder, as `{files}` in `run_tests`.
  - `check` is the commit gate, a local subset of what the CI runs: exit 0 green, else red; ends on its own (no watch mode, no prompt); changes no file (`--check`, not `--fix`: the tree is hashed before the run); local, no secrets or services; fast enough for every commit; deterministic; the cause of a red in its last lines. `init.md` looks for it as such, and the README gets a *check* section for a first install, with examples and how to try it on a clean main.
  - `integrate` stays as it is: `merge` only, and any other value refused with "not supported yet", so that the key is ready for the integrations to come.
  - `main` stays a key, default `main`, set by the human: `init` asks for it, proposing `main`, instead of deriving it from git (`origin/HEAD` is missing or stale too often for a guess).
  - Drop `reference` and `specs`: the test-author's throwaway model is the plugin's own, fixed at `.workflow/reference`; the L specs are in the plugin's format, fixed at `.workflow/specs`. `backlog` stays, default `.workflow/backlog.md`: like `rules`, it points to a thing of the project, which may keep a backlog of its own.
  - Rename `test_files` to `run_tests`: it is a command, as `check`, not a list of files, and it stood next to `tests_glob`, which is one.
  - Drop `stub`: stubs never reach main (stub mode does not commit, the implementer replaces them before the chunk's commit), so they are the plugin's own, like `reference`. The convention is fixed: a stub's body only throws an error whose type the runner reports as `NotImplemented` (Python's `NotImplementedError`; in TypeScript `Object.assign(new Error('not implemented'), { name: 'NotImplemented' })`), each agent writing it in the project's language.
  - `red_types` is measured by `init`, not asked: its red-check experiment (a test failing on an assertion, one calling a stub, one importing a missing module) reads the failure types of the first two from the JUnit XML and writes them. The detection counts as reliable only when both types are present, the stub's is the one the convention says, and neither shows up for the load error; otherwise `run_tests` stays empty and the red check is skipped, as today, and `init` tells the human why. Run twice, the experiment must give the same types.
  - `tests_glob` stays: it tells which files are tests, for `suite.sh` to record the suite and `commit.sh` to protect it; the test-author gets it as a bound on where tests go. Its default in `init.md` is aligned with the one in `lib.sh`.
  - Drop `probe_env`: no script read it, and the prober got it as a command with no contract on how to use it. The prober always works in a new temporary folder outside the repository, deleted at the end, and always inside an isolated environment of the language (a `venv`, a folder with its own `node_modules`), never a global install; its output says which environment it used.
  - `rules` stays: it points to the project's conventions, and with `commit` and `exec` gone it is the one channel for them. Two fixes: a decision record goes in a folder of `rules` that already holds decision records, and with none it is not written and the human hears it at the spec's checkpoint (`l-plan.md` today reads a folder out of the list); `init` looks for what Claude Code does not load by itself (decision records, `CONTRIBUTING.md`, `AGENTS.md`, convention docs) instead of keeping the `CLAUDE.md` default unseen. And `init` checks that the rule files state the branch and commit conventions and how commands run (a container, a wrapper), proposing to add them when they are missing.
  - `version = 2`, one migration: `require_config` refuses version 1 and says what to change. Every key change goes in `lib.sh`, `status.sh`, `init.md`, the README and the tests.

  Source: review of the config's responsibilities.
- **`/overload setup` in place of `init`: an agent proposes the config, the human settles it.** After the config v2 item and in the same release: both rewrite `phases/init.md`, and setup is how a project gets a v2 config. `init` is confused with Claude Code's own `/init`, which writes a CLAUDE.md. The flow:
  1. `/overload setup [guidance]` runs a new read-only agent, `setup-explorer`, with the human's guidance. It reads the project (manifests, CI workflows, scripts, `git log`, rule files) and returns the proposal whole, not pointers: a table of key, proposed value, source (`file:line`, or the command it came from) and certainty; questions only for what it could not settle, a key with no source being a question by construction; the gaps in the rule files (branch and commit conventions, how commands run) with the text to add. Not an explorer returning `file:line` for the main agent to read: the same files would be read twice. The rules on what makes a good `check` and the other values live in this agent.
  2. The main agent shows it; the human answers, counter-proposes, accepts or refuses. A subagent cannot talk to the human: the dialogue stays in the main agent, which applies the answers itself, reading a file at most, without running the agent again.
  3. On acceptance, the main agent writes the config and runs `verify.sh` on main, which must be green; no agent for one command, and a red needs the human.
  4. A new agent, `setup-red-probe` (Sonnet, low effort: a runner that does not collect a file needs a good retry, Haiku only after real runs), measures `red_types`: three minimal tests and a stub in the project's language inside `tests_glob`, run twice through `run_tests`, then deleted. Not the prober, which may not work inside the repository. The types are read by a script, a new `junit.py --types-found` printing each test's failure type, not by the agent. On failure it returns a diagnosis (a file not collected, the same type for an assertion and a load error) and changes no config.
  5. The results, the human's go, the commit, as today.

  Source: review of the config's responsibilities.
- **`integrate`: pull or merge requests on GitHub, GitLab and Bitbucket.** Today `integrate.sh` merges locally with `--no-ff` and refuses any other value. A project that integrates by PR/MR cannot use the plugin. The value is not a switch: the process is built on the local merge, and each forge needs its own tool (`gh`, `glab`, Bitbucket's API). To design first: where the metrics line goes, since it rides on the merge commit and a protected `main` takes no commit from the plugin; who checks the merge's result, today `check` on it, then the CI; where the last checkpoint is, the conversation or the PR's review; what happens to the journal, today dropped by the merge; whether squash and rebase merges are allowed, since squash erases the one-logical-change commits. Source: review of the config's responsibilities.
- **brainstorm: never run the explorer on a plainly S task.** `phases/brainstorm.md`, step 2, skips the explorer only for an S request "whose files you already know and have read", which at the start of a task is almost never: a docs-only backlog item ran it (about 70k weighted, a fifth of the task). On S the main agent reads the files anyway to change them, and finds the callers with `git grep`, so the explorer only adds a second reading and its report. New rule: explore only when the task may be L; a plainly S request reads its files itself. A task in doubt still explores, so the triage keeps its map; an S that turns L gets its map from `phases/l-plan.md`, which runs the explorer when no map is logged. Source: metrics of a run of S and L tasks.
